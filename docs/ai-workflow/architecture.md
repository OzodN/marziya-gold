# AI Engineering Workflow Architecture

## 1. Overview & Core Principles

This document defines the production-grade AI engineering workflow for this workspace. It is designed to orchestrate autonomous development by leveraging the native capabilities of the Antigravity runtime, avoiding brittle external frameworks. 

**Core Principles:**
1. **Explicit State Machines:** Workflows follow strict lifecycle states.
2. **Git as Source of Truth:** Code state, branching, and context persistence are anchored in Git.
3. **Independent Verification:** An agent claiming "it works" is insufficient. Success is determined by deterministic 0-exit codes from automated shell commands (tests, linters, builds).
4. **Least Privilege Agents:** Subagents are dynamically spawned with limited scopes, isolated workspaces, and specific toolsets.
5. **Human in the Loop (HITL):** High-impact decisions and architectural plans require explicit human approval gates before code execution.

---

## 2. System Components

* **Runtime:** Antigravity Agent Runtime.
* **Orchestrator:** The Root Agent (Lead Architect), operating in the primary workspace.
* **Workers:** Ephemeral, dynamically defined subagents running in isolated `branch` or `share` workspaces.
* **State Storage:** 
  * `.agents/state/task.md` (active checklist/state tracker)
  * `.agents/state/implementation_plan.md` (proposed architectural changes)
  * `.agents/state/walkthrough.md` (historical audit of what was done)
  * `.agents/rules/` (directory-scoped constraints for agent behavior)
* **Execution Engine:** Local terminal commands (`run_command`) simulating CI/CD loops and independent test execution.

---

## 3. Agent Roles & Hierarchy

The system relies on a strict hierarchical delegation model:

1. **Lead Orchestrator (Root Agent)**
   * **Role:** System manager, planner, and code reviewer.
   * **Capabilities:** Full read/write, subagent spawning, task delegation, repository merge rights.
   * **Workspace:** `inherit` (Main).
2. **Feature Builder (Dynamic Subagent)**
   * **Role:** Implementation specialist for a specific component or ticket.
   * **Capabilities:** `enable_write_tools = true`, no subagent spawning rights.
   * **Workspace:** `branch` (operates on fully isolated repository clones). `inherit` and `share` modes are strictly forbidden.
3. **Reviewer / Auditor (Dynamic Subagent)**
   * **Role:** Security, performance, or architectural reviewer.
   * **Capabilities:** `enable_write_tools = false` (Read-only).
   * **Workspace:** `inherit` (Inspects diffs generated by the Builder).
4. **Researcher (Built-in Subagent)**
   * **Role:** Explores documentation, codebase context, or web resources to answer unknowns without bloating the Orchestrator's context window.

---

## 4. Task Lifecycle (State Machine)

Every task follows a strict state transition model managed in `.agents/state/task.md`.

1. **`BACKLOG`**: Unprocessed user request or feature idea.
2. **`PLANNING`**: Orchestrator researches and drafts `.agents/state/implementation_plan.md`.
3. **`PENDING_APPROVAL`**: 
   * **Mechanical Human Gate.** For high-impact changes, the Orchestrator MUST generate `implementation_plan.md` using the `write_to_file` tool with `ArtifactMetadata.RequestFeedback = true`. This mechanically yields control to the user via a 'Proceed' button.
   * High-impact changes that **always** require approval: architecture changes, requirements changes, security model changes, destructive database operations, new external infrastructure/services.
   * Ordinary implementation tasks that do not meet these criteria may skip this state and transition directly to `IMPLEMENTATION`.
4. **`IMPLEMENTATION`**: 
   * Orchestrator spawns Feature Builder subagents.
   * Builders create a Git branch (`feature/<task>`) and write code.
5. **`VERIFICATION`**: 
   * Feature Builder messages the Orchestrator that implementation is complete.
   * **Root Orchestrator** checks out the feature branch and runs automated tests (`npm test`, `mvn verify`, etc.) via background tasks.
   * Loop: If tests fail, Orchestrator sends failure logs back to the Builder. Retry up to 3 times.
6. **`REVIEW`**: Orchestrator (or Reviewer subagent) diffs the feature branch against `main`. 
7. **`MERGE`**: Orchestrator merges the feature branch into `main`. Merge is IMPOSSIBLE until independent verification succeeds.
8. **`DONE`**: Update `.agents/state/task.md` and append to `.agents/state/walkthrough.md`.

---

## 5. Git Strategy & Parallelization

* **Branching Model:** `main` is the stable, protected branch. All work happens in short-lived `feature/*` or `fix/*` branches.
* **Workspace Isolation:** 
  * When executing tasks, the Orchestrator spawns Feature Builders using `Workspace: "branch"`.
  * This creates fully isolated workspace clones, allowing parallel subagents to write code concurrently without any filesystem collisions or stomping on the Root Agent's working tree.
  * **CRITICAL RULE:** The Root Agent must NEVER allow two write-capable subagents to operate on the same working tree. `Workspace: "inherit"` and `Workspace: "share"` must NEVER be used for write-capable subagents. If a branch workspace cannot be created, the task MUST immediately fail and escalate.
* **Merge Strategy:** The Orchestrator uses `git merge --no-ff` to preserve feature history, or squashes commits if requested by the user.

---

## 6. Verification Loop & CI Strategy

Agents are prone to hallucinating success. The system mandates **Independent Verification**:
1. A write-capable subagent must NEVER be trusted to certify its own work.
2. The Feature Builder may run tests locally for debugging, but its test result is informational only.
3. The Feature Builder must NOT mark the task as verified and is NOT the authority for the Definition of Done.
4. After the Feature Builder finishes, the **Root Orchestrator independently runs the verification commands** against the resulting branch.
5. Only an exit code of `0` from the Orchestrator's verification run satisfies the Definition of Done and permits merging.

---

## 7. Failure Recovery & Retry Limits

To prevent infinite loops of failing code, the following constraints apply:
* **Max Test Retries:** A Builder is allowed **3 attempts** to fix failing tests or lint errors.
* **Escalation:** If the limit is reached, the Builder must report failure to the Orchestrator via `send_message`.
* **Fallback State:** The task enters `BLOCKED_ESCALATED`, and the Orchestrator requests human intervention or pivots the approach.

---

## 8. Context & Memory Strategy

* **Short-Term Context:** Maintained via the `task.md` checklist. Subagents are given hyper-specific prompts containing *only* the context needed for their task to save context window space and reduce hallucinations.
* **Long-Term Memory:** 
  * Architecture decisions live in `docs/architecture/`.
  * Behavioral corrections are stored in `.agents/rules/*.md`. If a subagent repeatedly makes a formatting error, the Orchestrator can create a rule file that Antigravity will automatically inject into all future subagents modifying that directory.

---

## 9. Extension Points

* **MCP Integration:** Can be extended to connect to Jira/Linear (ticket tracking) or GitHub (PR management) via Model Context Protocol servers.
* **Custom Skills:** Complex, multi-step runbooks (like "How to deploy to staging") will be codified in `.agents/skills/<name>/SKILL.md` so agents can lazily load the knowledge only when required.

---

## 10. Major Risks & Trade-offs

1. **Context Exhaustion:** Large diffs sent via `send_message` between agents can bloat context. *Mitigation:* Agents should use Git tools (`git diff --stat`, `git diff > diff.patch`) and read files directly instead of pasting full code in messages.
2. **Infinite Loops:** An agent trying to fix a compiler error may get stuck. *Mitigation:* Strict 3-retry limit enforced by the Orchestrator.
3. **Flaky Tests:** Non-deterministic tests will stall the Verification phase. *Mitigation:* The Orchestrator can flag tests as flaky and escalate to Human Approval.
