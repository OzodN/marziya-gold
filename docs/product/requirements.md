# ТЗ / PRODUCT BRIEF
## Сайт-каталог ювелирных изделий мастера + система заявок + административная панель

Ты выступаешь как product/solution architect и senior full-stack engineer.

Твоя задача на этом этапе НЕ реализовывать проект и НЕ писать код.
Сначала проведи глубокий брейншторм по продукту, UX, бизнес-логике, архитектуре, модели данных и админ-панели.

Нужно:
1. внимательно изучить требования ниже;
2. выявить неоднозначности, слабые места и потенциальные проблемы;
3. предложить улучшения;
4. определить, какие решения нужно зафиксировать;
5. предложить оптимальную архитектуру;
6. предложить структуру БД;
7. предложить API;
8. предложить структуру frontend и admin panel;
9. отдельно проверить UX клиентской части;
10. НЕ добавлять ненужную e-commerce функциональность.

---

# 1. КОНЦЕПЦИЯ ПРОДУКТА

Нужно создать сайт для ювелирной компании / мастера.

Это НЕ классический интернет-магазин.

Основная задача сайта:
- показать каталог ювелирных изделий;
- дать клиенту максимально полную информацию об изделиях;
- позволить клиенту выбрать несколько изделий;
- указать количество каждого изделия;
- добавить их в корзину / подборку;
- отправить заявку продавцу;
- дать клиенту возможность напрямую связаться с продавцом через Telegram или телефон.

Цена изделий НЕ показывается на сайте.

Все изделия изготавливаются ПОД ЗАКАЗ.

Нет модели склада:
- нет остатков;
- нет "в наличии";
- нет "продано";
- нет резервирования;
- нет ограничения по доступному количеству;
- одно и то же изделие можно заказать в любом количестве.

Количество изделия клиент выбирает самостоятельно перед добавлением в корзину.

---

# 2. ОСНОВНОЙ CLIENT FLOW

Базовый пользовательский сценарий:

Главная
→ Каталог
→ Поиск / фильтрация
→ Карточка изделия
→ Просмотр подробной информации
→ Выбор количества
→ Добавление в корзину
→ Просмотр корзины
→ Заполнение контактной информации
→ Отправка заявки
→ Заявка появляется в админ-панели продавца

На странице товара также должна быть возможность:

[ Telegram ]
[ Позвонить ]

Эти контакты должны быть доступны клиенту напрямую.

Telegram и телефон НЕ являются частью механизма отправки заявки.
Это отдельный канал связи с продавцом.

# 3. ЦЕНА

Цена НЕ отображается на сайте.

Не нужно:
- payment;

- онлайн-оплаты;
- расчета доставки;
- промокодов;
- скидок;
- налогов;

Сайт не продает товар напрямую.

Сайт собирает запрос клиента.

# 4. ИЗДЕЛИЯ

- название;
- артикул;
- категорию;
- описание;
- изображения;
- динамические характеристики;
- 0..N камней.

Пример:

Название:
Кольцо Multibrand

Артикул:
GLD-0052-ULX

Категория:
Кольца

Описание:
...

# 5. ДИНАМИЧЕСКИЕ ХАРАКТЕРИСТИКИ ИЗДЕЛИЯ

Характеристики изделия НЕ должны быть жестко зашиты в модель Product.

Нельзя ограничиваться фиксированными полями вида:

weight
purity
color
material
collection
size
и т.д.

Вместо этого характеристики должны быть динамическими.

Формат:

name | value

Например:

Вес          | 2.20 г
Проба        | 585
Цвет         | Жёлтое золото
Материал     | Золото
Коллекция    | Design 2026
Производство | Ручная работа

Количество характеристик:
0..N

Мастер должен иметь возможность через админ-панель:
- добавить характеристику;
- удалить характеристику;
- изменить название;
- изменить значение;
- изменить порядок отображения.

Нельзя требовать участия разработчика для добавления нового параметра.

---

# 6. КАМНИ

У одного изделия может быть:
- 0 камней;
- 1 камень;
- несколько камней.

Каждый камень должен существовать как отдельный объект внутри конкретного изделия.

Например:

Product
 ├── Stone #1
 ├── Stone #2
 └── Stone #3

Для каждого камня должна быть отдельная информация.

---

# 7. ДИНАМИЧЕСКИЕ ХАРАКТЕРИСТИКИ КАМНЯ

Характеристики камня тоже НЕ должны быть фиксированными.

Нельзя создавать жестко заданную модель, где обязательно существуют только:

carat
color
clarity
cut
shape

Поскольку разные камни могут иметь разные характеристики.

Пример:

Камень:
Бриллиант

Характеристики:

Вес        | 0.50 ct
Количество | 1
Форма      | Round
Цвет       | F
Чистота    | VS1
Огранка    | Excellent

Другой камень:

Камень:
Сапфир

Характеристики:

Вес           | 1.20 ct
Количество    | 2
Форма         | Oval
Цвет          | Blue
Происхождение | Sri Lanka

У каждого ProductStone должно быть:
- название / тип камня;
- 0..N динамических характеристик;
- порядок отображения.

Мастер должен управлять этим полностью из админки.

# 8. UI КАРТОЧКИ ТОВАРА

Карточки товара должны быть визуально близки к предоставленным референсам.

Референсы находятся в текущем диалоге.

Общий принцип:

Левая часть:
- большая фотография;
- галерея;
- thumbnails;
- переключение изображений;
- zoom;
- на мобильном — swipe.

Правая часть:
- категория;
- название;
- артикул;
- основные характеристики;
- информация о камнях;
- выбор количества;
- добавление в корзину;
- Telegram;
- телефон.

Ниже:
- описание товара.

# 9. ИНФОРМАЦИЯ О КАМНЯХ НА СТРАНИЦЕ ТОВАРА

Если камней нет:
- блок не отображается.

Если есть один камень:
- показывается один блок.

Если несколько:
- отдельный блок для каждого камня.

Пример:

Информация о камнях

### Бриллиант
Вес        | 0.50 ct
Количество | 1
Форма      | Round
Цвет       | F
Чистота    | VS1

### Сапфир
Вес           | 1.20 ct
Количество    | 2
Форма         | Oval
Цвет          | Blue
Происхождение | Sri Lanka

UI должен быть аккуратным и легко читаемым.

# 10. КОЛИЧЕСТВО

Клиент сам выбирает количество изделия.

На странице товара:

Количество:
[ - ] 1 [ + ]

[ Добавить в корзину ]

Например:
Количество = 3
→ добавить 3 единицы товара.

Корзина должна позволять изменить количество после добавления.

Поскольку товары производятся под заказ:
- нет stock;
- нет availableQuantity;
- нет проверки складского остатка.

# 11. КОРЗИНА / ПОДБОРКА

Корзина используется не для оплаты, а для формирования заявки.

Возможно UI-терминологически лучше назвать ее "Моя подборка", но это нужно дополнительно обсудить.

Корзина должна содержать:
- изображение;
- название;
- артикул;
- количество;
- удаление;
- изменение количества.

Пример:

Кольцо Multibrand
GLD-0052-ULX
Количество: 2

Браслет золотой
GLD-0010-BC
Количество: 1

[ Отправить запрос ]

# 12. ЗАЯВКА

Заявка создается на основе содержимого корзины.

Минимальные данные клиента:

- имя;
- телефон;
- комментарий (опционально).

Можно предложить дополнительные UX-решения, но НЕ заставлять пользователя заполнять слишком много полей.

Пример:

Имя
Телефон
Комментарий

[ Отправить заявку ]

# 13. ЧТО ПОЛУЧАЕТ ПРОДАВЕЦ

Заявка должна появиться непосредственно в админ-панели.

НИКАКИХ:
- Telegram Bot;
- WhatsApp;
- email как основного механизма уведомления.

Основной канал уведомления продавца:
АДМИН-ПАНЕЛЬ.

Можно предложить варианты реализации realtime-уведомлений внутри сайта:
- polling;
- SSE;
- WebSocket.

Но для MVP выбрать рациональный вариант без избыточного усложнения.

---

# 15. СТАТУСЫ ЗАЯВКИ

Использовать следующие статусы:

NEW
CONTACTED
IN_PROGRESS
REJECTED
COMPLETED

Основной flow:

NEW
  ↓
CONTACTED
  ↓
IN_PROGRESS
  ↓
COMPLETED

Альтернативная ветка:

CONTACTED
  ↓
REJECTED

При этом не нужно запрещать администратору исправлять ранее установленный статус.

---

# 16. ОБЯЗАТЕЛЬНОЕ СОХРАНЕНИЕ ИЗМЕНЕНИЙ СТАТУСА

Изменение статуса НЕ должно автоматически сохраняться.

Пример:

Текущий статус:
CONTACTED

Администратор выбирает:
COMPLETED

Но пока он НЕ нажал:

[ Сохранить изменения ]

статус в БД не изменяется.

Если администратор случайно выбрал не тот статус и не сохранил:
изменения можно просто отменить уходом со страницы / сбросом.

Если администратор сохранил ошибочный статус:
он должен иметь возможность снова изменить статус и снова нажать:

[ Сохранить изменения ]

Это нормальный и обязательный сценарий.

Желательно также предусмотреть предупреждение при попытке покинуть страницу с несохраненными изменениями.

---

# 17. ИСТОРИЯ ИЗМЕНЕНИЙ СТАТУСА

Рекомендуется хранить историю:

oldStatus
newStatus
changedBy
changedAt

Пример:

21.09 14:32
NEW

21.09 15:04
NEW → CONTACTED

21.09 16:20
CONTACTED → IN_PROGRESS

22.09 11:15
IN_PROGRESS → COMPLETED

Предложи оптимальную модель и UX для этого.

# 18. ПОИСК

В каталоге обязательно нужен поиск.

Минимум:
- название;
- артикул.

Можно рассмотреть:
- описание;
- категорию;
- тип камня.

Поиск должен быть удобным и быстрым.

Предложи оптимальную реализацию поиска для PostgreSQL и выбранного backend/frontend стека.

# 19. ФИЛЬТРАЦИЯ

Обязательно нужны фильтры товаров.

Базовые фильтры могут включать:
- категория;
- материал;
- проба;
- цвет;
- коллекция;
- наличие камня;
- тип камня.

ВАЖНО:
характеристики товара динамические, поэтому архитектура фильтрации тоже должна это учитывать.

Нельзя превращать каждую характеристику в отдельное hardcoded Java-поле.

Нужно предложить:
- как определить, какие динамические характеристики могут участвовать в фильтрации;
- как хранить их;
- как строить запросы;
- как делать это эффективно.

- добавлять изображения;

- добавлять камни;
- удалять камни;

---

# 22. УПРАВЛЕНИЕ КАТЕГОРИЯМИ

Администратор должен иметь возможность:
- создавать категории;
- переименовывать;
- скрывать;
- менять порядок.

Категории НЕ должны быть жестко зашиты в enum в backend.

Пример:
Кольца
Серьги
Браслеты
Колье
Подвески
Цепи
Комплекты

Но UI и структура каталога должны оставаться стабильными.

Администратор не должен иметь возможности через CMS создавать произвольные уровни вложенности и ломать UX.

---

# 23. УПРАВЛЕНИЕ ТИПАМИ КАМНЕЙ

Типы камней должны быть управляемыми данными, а не enum.

Например:
Бриллиант
Сапфир
Рубин
Изумруд
Цирконий
Турмалин

Администратор должен иметь возможность добавить новый тип.

При этом механизм ProductStone + StoneCharacteristic остается фиксированным.

# 37. ОСОБЫЕ ПРАВИЛА ДЛЯ ТЕБЯ КАК AI-АГЕНТА

1. Не соглашайся автоматически со всеми требованиями.
2. Проверяй их на противоречия.
3. Если видишь плохое архитектурное решение — объясни почему и предложи альтернативу.
4. Не добавляй сложность просто ради "production-grade".
5. Приоритет: простота + поддерживаемость + хороший UX.
6. Не превращай проект в полноценный e-commerce.
7. Не превращай админку в полноценный page builder/CMS.
8. Динамичность должна быть там, где она действительно нужна:
   - товары;
   - характеристики;
   - камни;
   - характеристики камней;
   - категории;
   - контактные/операционные данные.
9. UI/UX и структура сайта должны оставаться под контролем разработчика.
10. Отдельно отмечай все места, где существует архитектурный trade-off.
11. Для спорных решений предлагай 2–3 варианта и затем рекомендуй один.
12. Не начинай реализацию до завершения анализа требований.
